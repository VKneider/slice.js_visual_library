DomService

Overview

DomService.reconcile() is the canonical way to render a variable-length list of child components. Give it your data and a stable key per item; it keeps the DOM, the component registry and the destroy lifecycle in sync.

Why it exists

The two obvious alternatives are both broken, in ways that only show up as a slow memory leak:

  • container.innerHTML = '' removes nodes without running beforeDestroy(). Every child's

document/window listeners, timers and registry entry survive. The framework never gets to clean up.

  • Re-creating a node (rather than moving it) re-runs its constructor and does the same thing.

So reconcile does three things, in this order:

  1. Refresh in place. For each item, find the existing node by its stable sliceId and update it.

Only a genuinely new item is built.

  1. Prune. Every child whose data is gone is destroyed with slice.controller.destroyComponent,

which runs beforeDestroy(). This happens before reordering so a dead node is never a reorder target.

  1. Enforce order, with the fewest moves. The DOM is moved to match items. insertBefore moves a node, it does not clone it, so no constructor re-runs. The nodes already in the right relative order (the longest increasing run of their current positions) stay put and only the rest move: moving the first item to the end is one move, not one per item. That matters beyond speed — a moved node loses keyboard focus and restarts its CSS animations.

Concurrency: renders queue per container, and coalesce

reconcile keeps one queue per container in a WeakMap. A render that arrives while another is still running waits for it instead of interleaving — otherwise the second could prune a node the first had just ordered, or both could decide to build the same id.

Renders that are still waiting coalesce: if three calls arrive while one is running, only the newest of the three is applied, and all three callers resolve when it is. A filter box that re-renders a list on every keystroke therefore applies the last keystroke, not every intermediate one.

Two details worth knowing, because both were bugs first:

  • The chain continues on failure. then(run, run) rather than then(run), so one bad render

cannot freeze every later render on that container.

  • The chain is dropped when it drains. A long-lived list does not accumulate one promise per

update.

The promise reconcile returns resolves once the DOM reflects *this* call's items or a newer call's. So await dom.reconcile(...) really does mean "the DOM is at least this fresh". A render that was superseded before it started is never applied — its own refresh and props callbacks do not run.

Adoption, and a build that returns nothing

Before paying for a build, reconcile looks for a direct child with slice-id="<key>" and adopts it (never a node nested deeper, which belongs to an inner list). The registry can lose track of a node — a build that failed part-way, a child the consumer pre-rendered and appended by hand — while the DOM still holds it, and building it again would throw already registered.

For the same reason the final ordered list is assembled from the nodes that actually exist rather than from the slots that were requested: slice.build legitimately returns nothing for an unregistered component name, and that must not shift every sibling by one.

Cost of a cold list

The first build is awaited on its own, because it warms the template cache; the rest then run in parallel. A cold list of *n* rows therefore costs one fetch per component type, not *n*.

API

  • keyOf(item) — the identity used across renders. Derive it from a stable id, never from the

array index: an index key makes item 1 keep its component (and its state) when it becomes item 2. It is also used to adopt an existing node, so it must be unique across the whole page, not just within this list — two lists using row-1 will fight over the same key.

  • props(item) — the props for one item.
  • refresh(node, props) — replaces the default slice.setComponentProps(node, props). Use it when

props are interdependent, or when the child builds sub-components asynchronously and needs its own update() in a specific order.

  • equals(previous, next) — optional. When it returns true for an item's data from the last render and its data now, that node is not refreshed (and props(item) is not called for it). Without it, every surviving node is refreshed on every render. Pass Object.is when you update data immutably (a changed row is a new object): re-rendering 1,000 rows after editing one then refreshes one. Do not use Object.is if you mutate item objects in place — the mutated row would look unchanged.

dom.destroyChildren(container) tears down every registered child at once.

Prop Scenarios

Best Practices

With immutable data, pass equals: Object.is. Re-rendering a long list after one row changes then touches one node instead of all of them.
Keys are page-wide sliceIds, not per-container. That is what lets an item move between two lists (a kanban column to another) and keep its component and state: reconcile the destination, then the source. It is also why two unrelated lists must not share key prefixes.
Call reconcile after every change to the data — a push, a filter, a re-sort — and nowhere else. Concurrent calls on the same container are queued rather than fought over, but two *different* data sources reconciling one container is still a design error: each will prune what the other just built.
await the call. The promise resolves after this render and any render already queued on the container, so a mutation that triggers two reconcile calls can still await once and know the DOM matches.
Reuse an item object across renders rather than rebuilding it, if the child keys off identity the object carries. TreeView keeps a WeakMap from item to a generated id for items with no path or id of their own, because an index key would hand item 0's component — and its open/closed state — to whatever took its place after a splice.

Pitfalls

Do not use the array index as keyOf. With an index key, inserting at the front makes item 1 inherit item 0's component — and its scroll position, its open/closed state, and its focus.
reconcile only manages direct children that carry a slice-id. Anything you append by hand inside the container is left alone; wrap it if it should be reconciled with the data.
Never spread an item straight into props. props(item) is assigned by name onto the element, and several common field names are getter-only DOM properties — children most of all — so props: (item) => item throws Cannot set property children and the row is silently never created. Forward only the keys the child declares.
