ConfirmActionModal

Overview

The "are you sure?" modal, and the single-value prompt. Built on [Modal](/docs/display/modal), so scroll-lock, focus, Escape and backdrop dismissal are already handled — this only owns the copy, the header mark, the two buttons and the answer.

Build it once, near your composition root, and recover it anywhere else:

Build exactly one. Unlike a Service, a Visual component is not a singleton: a second instance would also subscribe to confirm:request, so every question would open two dialogs.

The two ways in

1. A promise — when the answer decides what happens next

This is the better default and the one to reach for first. The alternative — a bare event plus callbacks — makes every call site juggle two async channels and a "did this already fire?" flag, and a caller that returns early leaves the event unfired. With a promise the control flow is linear and cannot get wrong.

2. The event manager — when the emitter cannot hold a reference

Some call sites genuinely cannot reach the component: a deep save routine, a store subscriber, a keyboard shortcut, a third-party callback. Emitting is then the sane move, and confirm:request is subscribed for you:

Nobody is waiting on the answer, so this is fire-and-forget: it opens, the user answers, the modal closes.

API

  • ask(options) -> Promise<boolean> — true confirmed, false cancelled or dismissed.
  • prompt(options) -> Promise<string|null> — the value, or null if cancelled.
  • isOpen (boolean) — whether a question is currently on screen.

Options for both (all optional):

Props set once on the component and overridden per call: confirmLabel, cancelLabel, confirmVariant, eventName.

The header mark

The icon in the header follows danger so a destructive question never looks like a routine one: exclamation-circle for danger, question-circle otherwise. Override it with any Icon name, or pass icon: false to show no mark at all.

The one invariant

Every ask()/prompt() resolves exactly once. A dialog that could be dismissed without settling would leave the awaiting caller hanging for the life of the page, so Escape, the backdrop, the X button, a second question arriving while one is open, and destroying the component all resolve — as cancellations. There is a spec for each of those.

Prop Scenarios

Best Practices

Put the consequence in message, not in the title. The title says what is being asked; the message says what happens if the answer is yes. "This cannot be undone" is worth more than "Confirm".
Use danger: true for anything irreversible. It swaps the confirm button, the header mark and the badge behind it in one property.
Prefer the promise over the event. Reach for the event when the emitter genuinely has no reference to the component, not because callbacks read nicely at the call site.

Pitfalls

required blocks the confirm button and paints an error, but it does not disable it. That is deliberate: a permanently greyed-out button tells the user nothing about why. If the empty case should not even be reachable, validate before opening the modal.

Do not pass singleton: true. That flag is only for components registered as "Service", and slice.build returns null for a Visual component built with it — so confirm.ask is then "not a function". Build the modal once and share it with slice.getComponent.

A prompt's field is focused when it opens, so Enter confirms. If the answer is not something a user should be able to submit with a single keystroke, do not put a prompt on that action.

ask() cannot prevent the modal from being dismissed — Escape and the backdrop always count as "no". If the answer must be explicit, do not make it cancellable: leave dismissable on and accept that a stray Escape reads as a refusal.

Every instance subscribes to confirm:request. Two instances means two dialogs for one question, so build exactly one, or give the second a different eventName.
