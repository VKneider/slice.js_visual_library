UnsavedChangesGuard

Overview

The "you have unsaved changes" guard. Any component can declare pending work with a stable key, and the guard covers the three ways a user can walk away from it.

API

  • arm(key = 'default', { message }) — declare pending work.
  • disarm(key = 'default') — the work is saved or deliberately abandoned.
  • isArmed / pendingCount — what is currently holding the guard.
  • confirmLeave(message?) -> Promise<boolean> — ask by hand, for anything the built-in exits miss.
  • guardFn(to, from, next) — the router guard body, if you want to compose it yourself.
  • setDialog(fn) — replace the browser confirm with your own dialog.
  • destroy() — release everything and detach the listeners.

Arms are reference-counted by key: arm('editor') twice is still one holder, and two different keys need two disarm calls. A component that re-arms on every render therefore cannot lock the user out of the page.

The three exits, and why they are not equally reliable

The back button is best effort, and cannot be otherwise

The router does not run beforeEach on popstate — Router.onRouteChange() goes straight to rendering. By the time the event reaches you, the URL has already changed.

So this service asks anyway, and if the answer is no it calls history.go(1) to put the history back. Two consequences are worth knowing:

  • The route you navigated away from can paint for a frame before being restored.
  • Only a single step back is reliably recoverable. Pressing Back three times in a row can

outrun the recovery.

The browser's native confirm is used on this path and your setDialog dialog is not, because a popstate handler has to answer synchronously or the browser moves on without it.

The browser owns the wording on beforeunload

Every current browser ignores any message you set and shows its own text. That is deliberate: a page that could name the consequence could also use it to trick people into staying. Expect "Changes you made may not be saved."

Browsers also only honour the prompt after the user has interacted with the page at least once.

Prop Scenarios

Composing with your own router guard

The router keeps guards in a single slot (router._beforeEachGuard), so registering a second one replaces the first. This service composes with whatever was already there at the moment it was built — but an app that registers a guard *afterwards* replaces this one. If that is you, compose explicitly:

In Slice.js 4.x, next(false) does not cancel the navigation. Router._executeBeforeEachGuard ends with return redirectPath ? { path: redirectPath, … } : null, and false is falsy, so the cancellation branch is unreachable — the router proceeds with a warning-free "success". If you need to cancel a navigation, throw from the guard instead: the router's catch returns { path: false }, which does cancel. next('/some/path') redirects correctly and is unaffected. ## Best Practices
Disarm on save success, not on save click. Disarming optimistically loses the user's work if the save fails.
Use a different key per form. Two forms on one page then warn independently, instead of one saving silently switching the other's guard off.

Pitfalls

Arming is not the same as validating. The guard warns about leaving; it does not check that what the user typed is worth keeping.
Do not arm for trivial state — a collapsed panel, a ticked checkbox, a search filter. A guard that fires on things nobody would mourn is a guard the user learns to dismiss without reading, which costs you the warning you wanted for the one case that mattered.
beforeunload cannot be styled or worded. If the confirmation must be your own design, you cannot cover page close with it — only in-app navigation, through confirmLeave() or setDialog().
