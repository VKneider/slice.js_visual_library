HtmlService

Overview

HtmlService is a Service component: a plain logic class (no DOM, no template) that makes it safe to turn an HTML string into real markup.

Most of the library never needs it, and that is the point — every visual component here assigns textContent, so it cannot produce markup injection at all. Reach for this service only at the boundary where HTML you did not write enters your app: a CMS field, a markdown renderer, a template someone imports, a comment left by another user.

Requires an npm dependency

This is the one component in the library that is not dependency-free:

slice get HtmlService prints a warning naming the package if it is missing.

Three layers, in increasing paranoia

sanitize() is the net *underneath* esc(), not a replacement for it. Encode as you interpolate, sanitize as the final gate before the innerHTML assignment.

Best Practices

Sanitize at the boundary, once, when the value enters — not at every render site. Then the value is just data for the rest of its life, and a new render path cannot forget to sanitize.
sanitize() already passes inline SVG through unchanged, including viewBox and path. There is no need to widen the tag or attribute allowlist to make icons work — doing so only widens the attack surface.

Pitfalls

innerHTML = value with an unsanitized value is an XSS hole even when the value "only" comes from your own database: anything that writes to it — a form field, an import, a support tool — turns it into a hole too. sanitize() at the boundary closes all of them at once.
Do not use sanitize() on content written by someone else. It allows <img>, so <img src="https://tracker.example/pixel.gif"> survives — and that leaks the reader's IP address and User-Agent the moment the page renders, with nothing visible on screen. Use sanitizeRichText(), which drops images entirely. Links are kept on purpose: an <a href> only reaches its destination when the reader deliberately clicks it, and the destination is visible first.
sanitizeRichText() drops tags but keeps their text, so a stripped <img> simply disappears while <script>alert(1)</script> leaves alert(1) as visible text. That is DOMPurify's KEEP_CONTENT behaviour, not a bug — but if you are rendering user comments, use toText().
Sanitizing is not the same as validating. sanitize() guarantees the string is safe to become markup; it says nothing about whether the content is *correct*. Check the shape of the data too.
