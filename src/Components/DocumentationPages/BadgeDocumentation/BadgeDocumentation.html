Badge

Overview

A Badge is a small status pill: a count, a label, or a bare dot. It answers "what state is this thing in" at a glance, next to a list item, a tab, an avatar or a button.

Variants are semantic (success, danger, warning, info, accent), not decorative, and each derives from its own theme token — --success-color, --danger-color, --warning-color, --info-color, --primary-color — so a badge means the same thing in light and dark without you picking a colour.

The five coloured variants were separated by measurement, not by eye: all ten pairs clear a CIE ΔE of 36 or more, so none of them reads as another. The hues sit in distinct bands — danger 0°, warning 32°, success 161°, info 213°, brand 271°.

Variants are tinted, not solid: a soft wash of the status colour, a hairline border, and text in a readable shade of that same colour. A solid fill was measured at 3.19–3.77:1 for white text on the lighter status colours, under the 4.5:1 AA bar for 12px text, and five saturated fills in a row read as a traffic light rather than as badges.

API

  • variant (neutral | accent | success | warning | danger | info, default neutral)
  • label (string) — the text. Doubles as the accessible name when dot is set.
  • value (number | null) — a count. Wins over label, and is capped by max (99 → 99+).
  • max (number, default 99) — the cap for value.
  • dot (boolean) — render a bare dot instead of text.
  • size (sm | md, default md)

Prop Scenarios

Theming

Badge needs one token per status colour beyond the standard palette: a readable shade, the version of that colour that clears 4.5:1 against its own tint on the current theme's surface.

The shade has to move in opposite directions per theme. Light darkens the status colour toward black; dark lightens it toward white, because a dark theme's status colours are already light and darkening them produces a mid-tone with no contrast on a dark surface. Getting this wrong is not subtle — measured on the wrong direction, five of six variants land between 3.00:1 and 4.05:1 in dark mode.

The -readable tokens are optional for a light theme. Each color in Badge.css carries the light-tuned value as a fallback, so a theme with only the standard tokens still renders between 4.89:1 and 5.38:1. They are effectively required for a dark theme: without them, dark badges fall to 3.00–4.05:1. That fallback is not belt-and-braces. slice init copies the framework's src/, themes included, so a new app's theme is slicejs-web-framework's Light.css — 21 tokens, and its only shade is --primary-color-shade, a *border* tone. None of the five above are in it.
--primary-color-shade is a different token. It is a border/surface tone of the brand, used in ~40 declarations across 15 components and Required by the component standards. --primary-color-readable is the *text* tone, for text sitting on a tint. The -readable suffix exists to keep the two apart. There is no --accent-color. It measured at 3° of hue and 1.52:1 from --secondary-color — a duplicate rather than a third colour — and in the wild "accent" already means *the brand*, which is --primary-color here. The accent variant survives and is purple; only the redundant token is gone.

Best Practices

Overlaid on a button or an avatar, keep the badge absolute in your own layout — Badge only styles itself, not its position relative to a sibling.

Pitfalls

Colour alone is not enough of a signal. A danger badge next to a success one reads differently to everyone, but only the text tells a colourblind user which is which — keep label or value set.
